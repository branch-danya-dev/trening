# Тренировки и тело

Одно веб-приложение для любого устройства:

- **Тренировка** — расход калорий при ходьбе и беге на дорожке и на улице: независимая проверка цифр
  Apple Watch, которые на дорожке с уклоном сильно ошибаются, и журнал тренировок.
- **Модель тела** — 3D по замерам и фото, с прогнозом, как тело изменится при заданном питании
  и тренировках, и слежением за планом.

Замеры, тренировки и фото не покидают устройство.

*feat. Claude* — код, модели и проверки написаны вместе с Claude (Anthropic).

## Запуск

Одно веб-приложение — расчёт тренировок, модель тела, прогноз и фото:

```bash
dotnet run --project src/WorkoutCalculator.Web
```

Приложение поднимется на http://localhost:5256 и откроет браузер. Нужен только .NET 10 SDK:
дополнительные рабочие нагрузки (`wasm-tools`) и Node.js не нужны, three.js лежит в репозитории.

Опубликованная версия — https://branch-danya-dev.github.io/trening/ (обновляется при каждом пуше в main,
см. «Публикация» ниже). Её можно открыть с телефона и установить как приложение: в Safari — «Поделиться →
На экран „Домой“», в Chrome — «Установить приложение». Установленная версия работает и без интернета.
Как проверять на реальных данных и что прислать — [docs/TESTING.md](docs/TESTING.md).

Тесты всего решения:

```bash
dotnet build WorkoutCalculator.sln
dotnet test WorkoutCalculator.sln
node --test tests/js/*.test.mjs
```

На каждый PR и пуш в main GitHub Actions собирает решение и прогоняет тесты (`.github/workflows/ci.yml`).
Решение открывается в Visual Studio и Rider; все проекты — на .NET 10.

## Геометрия тела и skeletal viewer

`BodyProfile` задаёт идентичность тела: замеры, состав, форму и привычную осанку.
`IBodyShape.Geometry` возвращает `BodyGeometry`: готовый `BodyMesh` и необязательный `SkeletonPayload`.
Это персональная rest-форма; runtime-поза и анимация хранятся отдельно в `skeletal.js` и не меняют
профиль, вершины для расчётов, обхваты, ленты-источники или прогноз. `Home.razor` только передаёт
геометрию через `ViewerInterop.SetGeometry`.

**Осанка в этом этапе остаётся в геометрии.** Подгонка MakeHuman измеряет уже поставленное тело,
а `PostureRig` переносит в эту позу последующие таргеты и слой мягких тканей. Заменять его одним
финальным набором GPU-поворотов без пересмотра подгонки нельзя. Runtime rig получает суставы из
той же готовой формы; baseline-повороты повторно не применяются. Сброс runtime-позы возвращает
точно эту персональную форму, включая осанку. Перенос осанки целиком в baseline transforms — отдельная
работа с проверкой эквивалентности всей подгонки.

- `RigDefinition` содержит только имена, иерархию и по четыре индекса/веса для **вершин тела**.
  Определение лениво создаётся один раз на `MakeHumanModel`, в JS передаётся один раз на слот.
- `MakeHumanRig` строит rest transforms по суставам: +Y вдоль кости, X по `rotation_plane`,
  с устойчивой заменой оси для вырожденной плоскости. Смещения и кватернионы переводятся в систему
  родителя. На кость передаются семь `float32`: `px,py,pz,qx,qy,qz,qw` (для 104 костей — 2912 байт).
- Позиции, индексы, родители, rest transforms и skin идут через `MemoryView`; JS копирует каждый
  буфер до возврата из вызова. Веса остаются `uint8`, сумма 255, атрибут `skinWeight` — normalized
  UNORM8 (в CPU/GPU получается сумма 1). Вершины и веса через JSON не проходят.
- `current` и `forecast` имеют отдельные `THREE.SkinnedMesh`, кости, inverse bind matrices и mixers.
  Bind вычисляется в персональной rest-форме до сдвига слотов в режиме «рядом». При смене геометрии
  старая анимация останавливается, bone texture освобождается, новый слот начинает с rest-позы.
  Манекен и старые данные без скелета используют `THREE.Mesh`.
- Оба прохода ghost-контура используют скелет текущего тела; шейдер контура преобразует также нормали.
  Ленты следуют за скелетом своего тела по весам ближайших вершин rest-поверхности. Это визуальная
  привязка: обхваты остаются измерениями rest-формы, при анимации заново не измеряются.

Минимальный API (консоль браузера; доступен также через `ViewerInterop`):

```js
const viewer = await import(new URL('js/viewer.js', document.baseURI));
// Полная разреженная поза: неуказанные кости сбрасываются в rest.
// xyzw — дельта в локальных rest-осях: qLocal = qRest * qDelta.
viewer.applyPose('current', { 'lowerarm01.L': [-0.5, 0, 0, Math.sqrt(0.75)] });
viewer.resetPose('current');
viewer.playDemo('forecast'); // один 2-секундный AnimationClip, затем rest
```

`playDemo` — только техническое сгибание руки, без библиотеки упражнений, IK, ограничителей суставов
и анатомической валидации движения. Rig линейный; при больших поворотах возможны артефакты.
Ориентация по персональной rest-форме не является готовым контрактом ретаргетинга внешних клипов.
Frustum culling отключён для двух skinned-тел и их followers: анимация может выйти за rest-bounds.
Камера по-прежнему вписывается по росту тела; произвольные экстремальные позы могут выйти из кадра.

Проверки rig входят в обычные `dotnet test` и `node --test tests/js/*.test.mjs` (используется локальный
three.js, без npm-зависимостей). Дополнительный браузерный тест проверяет настоящий Blazor interop,
bind-позу всех вершин, смену осанки, два слота, ghost, ленты, камеры, анимацию, MP4/WebM и возврат
к манекену. Для него отдельно нужны Playwright и Chromium; после запуска приложения:

```bash
node tests/browser/skeletal-smoke.cjs
```

`APP_URL` меняет адрес приложения (по умолчанию `http://127.0.0.1:5256`), `BROWSER_CHANNEL=chrome`
выбирает установленный Chrome, `NODE_PATH` позволяет использовать уже установленный Playwright.
`RIG_SCREENSHOT` задаёт необязательный путь снимка. Тест не добавляет диагностический API в приложение.

## Runtime-анимации упражнений

Skeletal viewer поддерживает отдельные rotation и translation tracks: вращения задаются quaternion-дельтами
от персональной rest-позы, смещения — долями роста тела, поэтому клипы не привязаны к одному росту.
`joint-constraints.js` ограничивает явно невозможные углы основных суставов; это защитные диапазоны,
а не медицинская модель биомеханики.

Определения движений вынесены из viewer в `exercise-animations.js`. Первые пять клипов:
**присед, жим лёжа, сгибание рук, тяга верхнего блока и румынская тяга**.
Viewer предоставляет общий API `playAnimation / stopAnimation / setAnimationTime`; последний нужен
для scrub/timeline и тестов. В интерфейсе на режиме «Сейчас» у MakeHuman есть компактный выбор упражнения
и запуск/остановка анимации.

Пока нет оборудования, IK, коллизий и физического расчёта техники. Жим выполняется на условной
«воздушной» скамье; эти клипы — первый анимационный слой перед каталогом упражнений и MuscleLoadEngine.

## Расчёт тренировки — вкладка «Тренировка»

Мастер в три шага: какая была тренировка → параметры → данные с часов, затем итог.

- **Профиль** общий с моделью тела: пол, возраст, рост, вес — с вкладки «Параметры»; пульс покоя
  и VO2max (необязательно) вводятся на первом шаге и сохраняются в профиле.
- **Дорожка:** длительность, скорость, уклон (если они менялись по ходу — несколько отрезков), поручни,
  дистанция с табло для сверки.
- **Улица:** дистанция, время, набор высоты, покрытие.
- **Часы:** средний пульс, активные и общие ккал, дистанция — для сравнения.
- **Итог:** активные калории (оценка), всего и разброс методов, сравнение с часами, скорость, темп,
  пульс, МЕТ, таблица методов и примечания.
- **Журнал:** «Сохранить в журнал» с датой; последние 4 недели (тренировки, время, активные ккал)
  против кардио по плану выбранной гипотезы, список тренировок с цифрой часов. Хранится на устройстве.

Время можно вводить как `30`, `30,5` или `30:23`; дробные числа — через запятую или точку. Ошибка
в поле показывается под карточкой, и фокус переходит на это поле. На телефоне на этой вкладке 3D-вид
спрятан — мастер на весь экран.

### Методы расчёта

| Метод | На чём основан | Источник |
|---|---|---|
| ACSM | скорость, уклон, время | ACSM's Guidelines for Exercise Testing and Prescription |
| Минетти | уклон, дистанция (учитывает спуск) | Minetti et al., J Appl Physiol, 2002 |
| Кейтел | пульс, вес, возраст, пол | Keytel et al., J Sports Sci, 2005 |

Итог — среднее по методам. Пульсовая оценка исключается из итога, если на долгой тренировке
она сильно выше механической (дрейф пульса) или пульс ниже 90.

Дополнительно: базовый обмен — Миффлин — Сан Жеор, максимальный пульс — Танака,
сопротивление воздуха при беге на улице — +1% уклона (Jones & Doust, 1996),
поручни — −20% к механическим методам.

Результаты — оценка, а не медицинское измерение.

## Модель тела, прогноз и фото

Тело строится по замерам — на основе MakeHuman или процедурным манекеном, — а режим гипотез показывает,
как оно может измениться за N недель при заданном питании и тренировках. Это проверка идеи,
а не финальный продукт.

### Интерфейс

На компьютере 3D-вид слева, панель справа. На телефоне вид сверху, панель снизу со своей прокруткой: тело
остаётся на экране, пока двигаешь ползунки. Вместо четырёх кнопок камеры там одна — ракурсы по кругу.
Телефон боком — вид и панель рядом. Модель всегда вписывается в кадр под кнопками и не прячется за ними.

- Слева 3D-вид: вращение мышью, зум колесом, кнопки «Спереди», «Сбоку», «Сзади», «Сброс камеры».
  Режимы «Сейчас», «Прогноз», «Сравнение». В сравнении текущее тело — светящийся контур поверх прогноза:
  видно, где тело уменьшится (контур снаружи) и где вырастет (контур уходит внутрь). Галочка «рядом»
  ставит модели бок о бок. Кнопка «● Видео» записывает 6-секундный оборот модели в текущем режиме
  (MP4 или WebM — что умеет браузер) и сохраняет файл на устройство.
- Сверху переключатель модели «MakeHuman / Манекен», выбор запоминается. Данные MakeHuman (~2 МБ)
  грузятся в фоне, до загрузки показывается манекен.
- Галочка «ленты замеров» в левом нижнем углу показывает на теле, где меряется каждый обхват; лента
  обхвата подсвечивается оранжевым и без галочки — когда мышь над его полем или поле в фокусе.
- Справа вкладка «Параметры»: пол, возраст, рост, вес, % жира и обхваты: грудь, талия, бёдра, плечо, бедро;
  шея, голень и запястье — необязательно (галочка «Указать: …»), иначе оцениваются по данным ANSUR II.
  У каждого — ползунок и поле, в поле можно писать с запятой. Под % жира — оценка по обхватам (формула
  ВМС США) с кнопкой «Подставить»; без обхвата шеи формула не работает. Производные значения (безжировая
  и жировая масса, ИМТ, талия/рост) только показываются.
- Вкладка «Тренировка» — расчёт тренировки и журнал (раздел «Расчёт тренировки» выше).
- Вкладка «Гипотеза»: срок, калории в день, бытовая активность, кардио и силовые, целевой вес
  (необязательно). Результат — итог (жир, безжировая ткань, вода и гликоген по отдельности, насколько
  подстроится обмен), предупреждения, таблица «было → станет», график веса по неделям. Карточка
  **«Факт против прогноза»** — взвешивания и фотосессии начатого плана рядом с прогнозом
  (раздел «Прогресс по фото и факт против прогноза»).
- **Несколько гипотез** — до 5, каждая под своим названием. «+ Копия» добавляет вариант выбранной гипотезы,
  название меняется в поле «Название», удаление — с подтверждением. Кнопки «Сохранить» нет: изменения
  сохраняются сразу. Редактор и 3D-вид показывают выбранную гипотезу; выбрать её можно чипом вверху вкладки,
  заголовком столбца в сравнении, легендой графика или списком в 3D-виде (в режимах «Прогноз» и «Сравнение»).
  Таблица «Сравнение гипотез» показывает план (срок, питание, кардио, силовые, средний баланс) и итог к концу
  срока (вес, % жира, жир, безжировая ткань, обхваты, число предупреждений). На графике веса у каждой гипотезы
  своя линия, подсказка при наведении показывает все линии сразу. Цвет закреплён за гипотезой и не меняется,
  когда соседние удаляют. Соседние цвета палитры различимы и при дальтонизме (проверено по ΔE в OKLab
  с имитацией протанопии и дейтеранопии), контраст с фоном — не меньше 3:1.
- Карточка **«Осанка и форма»** на вкладке «Параметры» (только для MakeHuman): наклон таза, прогиб
  в пояснице, сутулость и плечи вперёд — в градусах; живот, ягодицы, глубина корпуса и V-силуэт —
  от −100 до 100 при тех же обхватах. Подробно — в разделе «Скелет, осанка и форма». Обычно их
  заполняет подгонка по фото.
- Вкладка **«Фото»** — съёмка с подсказками или готовые снимки, разбор силуэта, обхваты по фото
  и подгонка модели под снимки (раздел «Аватар по фото»); сравнение сессий, прогноз на снимке и защита
  PIN-кодом (раздел «Прогресс по фото и факт против прогноза»).
- Профиль, гипотезы и выбранная модель хранятся в localStorage браузера. Поля профиля `Sex`, `Age`,
  `HeightCm`, `WeightKg` названы как в `UserProfile`. Если сохранённого профиля нет: мужчина 180 см, 78 кг,
  14 % жира. Гипотеза, сохранённая прежней версией (одна, без названия), открывается как «План 1».
- В правом нижнем углу вида — модель, число вершин, время построения сетки, передачи её в JS и проверки замеров.
  Внизу вкладки «Параметры» — «сборка xxxxxxx» (коммит, из которого собрано приложение): видно, обновилась
  ли установленная версия.
- Под разбором фото — «Отчёт для проверки»: профиль, ширина и глубина на ключевых уровнях, обхваты по фото
  против ленты и итог подгонки текстом, без снимков, — чтобы прислать при проверке.

### Модель MakeHuman (по умолчанию)

Реалистичная форма тела, которую процедурным манекеном не получить: базовая сетка MakeHuman hm08
(только тело — 13 380 вершин) и её таргеты. Используются только ассеты MakeHuman под **CC0 1.0** — сетка
и таргеты, переведённые в компактный бинарный файл `wwwroot/data/makehuman-hm08.bin` (источник, коммит
и команда пересборки — в `wwwroot/data/README.md`). Код MakeHuman (AGPL) не используется: загрузка,
подгонка и замер написаны заново в `BodyModel/MakeHuman`.

Как строится тело (`MakeHumanModel.cs`):

1. **Макро-таргеты** — пол, возраст, мускулатура, полнота. Мускулатура и полнота считаются по индексам
   безжировой и жировой массы (кг/м²) относительно типичных для пола; константы — оценки прототипа
   (`MakeHumanMapping.cs`). Расовые таргеты MakeHuman усредняются — внешность нейтральная.
2. **Масштаб под рост**, ступни на полу.
3. **Таргеты замеров** MakeHuman подгоняют обхваты на 10 уровнях с точностью 0,5 мм: введённые (тест: ≤ 1 %),
   а где замеров нет — оценки ANSUR II (тест: ≤ 2 %): неуказанные шея, голень и запястье, а ещё низ бедра
   над коленом и щиколотка (таргеты knee-circ и ankle-circ). Без колена и щиколотки бедро полного человека
   «проваливалось» над коленом. Обхват меряется «лентой»: сечение сетки плоскостью на тех же уровнях, что
   у манекена (у рук, ног и шеи — поперёк сегмента, по суставам MakeHuman), длина — по выпуклой оболочке
   сечения, как у натянутой ленты. У части мужчин подмышки MakeHuman оказываются ниже уровня груди
   по ANSUR II, и плоскость груди задевает руки — тогда лента груди опускается шагами по 0,5 % роста,
   но не больше чем на 3 %. Вес таргета замера ограничен ±3: с прежним ±2 у 8 % мужчин ANSUR II
   не подгонялась талия.
4. **Слой мягких тканей.** Даже с подогнанными обхватами тело MakeHuman выходит на 6–7 % меньше по объёму,
   чем следует из веса и % жира, у полных — на 11–13 %. Поэтому поверх формы кладётся слой вдоль нормалей,
   подобранный так, чтобы объём сошёлся с весом (тест: ±3 %), и обхваты подгоняются заново. Слой лежит
   по зонам тела (веса скелета MakeHuman, тоже CC0; коэффициенты — `SoftTissue.cs`): полностью на животе,
   боках, верхе спины и ягодицах, тоньше на руках и голенях, почти нет на кистях, стопах и лице. На бёдрах
   его нет: там таргеты замеров снимают слой целиком, и он только портил форму. На шее слой гасится по доле
   зоны шеи у вершины, иначе он затекал с плеч и тонкую шею нельзя было подогнать. Раньше слой был
   равномерным, и у полных профилей кисти становились «варежками», а лицо — раздутым.
   Толщина слоя (от −15 до +45 мм в самой толстой зоне) видна на вкладке «Параметры». Подбирается она
   за 1–3 перестройки тела. После слоя таргеты снова подгоняют обхваты и снимают бо́льшую часть добавленного
   объёма: остаётся около 0,28 «площади слоя × толщину» (у людей ANSUR II — от 0,1 до 0,4). С этой долей
   делается первый шаг, дальше — секущая по измеренному наклону, если он правдоподобен. Для очень больших
   размеров (талия больше ~130 см) формы MakeHuman не хватает: подсказка говорит, на сколько модель
   меньше, чем по весу, — это предел модели, а не ошибка в замерах.

**Проверка на людях ANSUR II** (`AnsurFit --validate`, по 300 человек каждого пола, ниже). Введённые
обхваты не подгоняются у 3,3 % мужчин и ни у одной женщины (до исправлений шага 4 — у 10,7 % и 2,7 %).
Все такие мужчины полные (ИМТ 30–41): талия или бедро выходят на 1–6 % меньше введённых, у одного шея —
на 4 % больше, и на экране об этом есть подсказка. Слой у 90 % людей — от −15 до +29 мм у мужчин и от −12
до +26 мм у женщин. Объём сходится с весом в пределах ±3 % у 96 % мужчин и 99 % женщин. Остальным нужен
слой тоньше нижнего предела: форма MakeHuman с их обхватами объёмнее тела, чаще у полных. Если утончать
слой дальше, таргеты замеров не успевают вернуть талию и бёдра. Замеры от этого не страдают — их
проверяет манекен.

Пока ползунок обхвата движется, подгонка стартует с прошлого решения, а слой не пересчитывается: ~20 мс
на сборку, 45–55 мс, если меняются пол, возраст, рост, вес или % жира (пересчитываются макро). Через
150 мс после остановки — точная сборка со слоем под вес, ~150 мс. С лентами замеров — ещё ~20 мс.

### Скелет, осанка и форма

У прежней модели спина всегда была ровной: таргеты MakeHuman меняют обхваты, но не осанку. Теперь в файле
данных (формат 3) есть **скелет MakeHuman** (`rigs/default.mhskel` и его веса, тоже CC0): 104 кости —
позвоночник, шея, голова, руки и ноги с пальцами; лицевые кости слиты с головой. У каждой вершины до четырёх
костей с долями — столько же берёт three.js, так что анимации тренировок и подсветка мышц потом лягут на
тот же скелет. Суставы — вершины сетки (центры вспомогательных кубиков MakeHuman), поэтому после таргетов
скелет сам подстраивается под тело. Файл данных вырос с 2,1 до 2,3 МБ.

**Осанка** (`Posture`, `PostureRig.cs`) — повороты костей и линейный скиннинг. Человек при этом стоит прямо:

| Ползунок | Что делает | Пределы |
|---|---|---|
| Наклон таза | таз поворачивается вокруг оси тазобедренных суставов, ноги на месте, поясница возвращает корпус к вертикали — поэтому прогиб глубже | −10…+15° |
| Прогиб в пояснице | меняется только дуга поясницы: вершина разгибается, низ и верх сгибаются так, что таз и грудь остаются на месте (+20° — вершина дуги на 1,6 см глубже) | −15…+20° |
| Сутулость | верх спины сгибается, половину наклона забирает грудопоясничный отдел, остаток — шея: взгляд вперёд, голова уходит вперёд (+20° — лицо на 6–7 см впереди) | −15…+25° |
| Плечи вперёд | ключицы поворачиваются вокруг грудино-ключичного сустава | −10…+20° |

Руки при любой осанке висят вертикально; обратный поворот руки разделён между плечевым суставом и серединой
плеча — в одном суставе он сминал кожу подмышки. При заданной позе вершина — `B·p + c` (смесь преобразований
костей по её весам), поэтому слой мягких тканей и таргеты замеров добавляются к исходной форме и точно
переносятся в позу. Обхваты, рост и объём меряются **в позе**: сутулый человек ниже, и его рост в позе
совпадает с замером.

**Форма** (`BodyForm`) — таргеты MakeHuman от −1 до 1: живот (`stomach-pregnant`), ягодицы
(`buttocks-volume`), глубина корпуса (`torso-scale-depth`), V-силуэт (`torso-vshape`). Обхваты подгонка
возвращает к замерам, поэтому меняется распределение: при той же талии живот выступает вперёд, а бока уже.
Таргет живота MakeHuman — беременность, после 0,6 живот провисает складкой, поэтому +100 на ползунке —
0,6 таргета.

Сдвиг ползунка осанки или формы перестраивает тело за 75–95 мс (обхват — за 15 мс: форма берётся из кэша).

### Аватар по фото

Вкладка «Фото». Снимки хранятся только на устройстве, разбор и подгонка идут в браузере.

- **Хранение.** Сессии съёмки — в IndexedDB браузера. Снимки уменьшаются до 2048 пикселей по длинной стороне
  и перекодируются в JPEG: поворот по EXIF применяется, а метаданные (в том числе геопозиция) не сохраняются.
  Архив zip — сохранить на устройство и загрузить обратно (например, на другой телефон). Приложение просит
  браузер не стирать данные при нехватке места; надёжнее установить его на главный экран.
- **Съёмка с подсказками.** Камера в браузере и распознавание позы MediaPipe Tasks Vision 1.1.0 (Apache-2.0,
  лежит в `wwwroot/lib`, ~23 МБ: модель позы и WebAssembly; в офлайн-кэш попадает при первой съёмке). Два
  шага: спереди — лицом к камере, руки чуть в стороны, ноги на ширине таза; сбоку — руки вдоль тела, **ноги
  вместе**. Приложение голосом и текстом подсказывает, что поправить (отойти, встать по центру, опустить
  руки…), и само делает снимок, когда человек замер. Можно и загрузить готовые снимки из файлов.
- **Разбор силуэта** (`SilhouetteProfiler.cs`). Маска фигуры (MediaPipe) делится на связные куски —
  берётся тот, где таз. Края уточняются по перепаду яркости снимка. Масштаб — рост, делённый на высоту фигуры;
  уровни от 30 до 86 % роста через 0,5 % отсчитываются от макушки — низ стоп искажён перспективой. Масштаб
  снимка спереди переносится со снимка сбоку: там носки не тянутся к камере. Уровни, где к краю тела
  подходит рука, помечаются и в расчёты не идут. На снимке модели MakeHuman ширина и глубина груди и талии
  совпали с сечениями сетки в пределах 0,3–1 см; глубина бёдер — на 2,5 см меньше: у модели ступни
  разведены, и перспектива сбоку сдвигала уровни (при съёмке ноги вместе).
- **Обхваты по фото** (`PhotoGirths.cs`). Талия и бёдра — по ширине спереди и глубине сбоку, линейные
  регрессии ANSUR II, ошибка 1,5–1,8 см (эллипс с поправкой был точнее не лучше). В таблице разбора они
  стоят рядом с замером лентой — сильное расхождение значит, что стоит перемерить или переснять. Груди
  нет: в ANSUR II ширину груди мерили циркулем под мышками, без широчайших мышц (у мужчин в среднем 28,9 см —
  уже талии), и с шириной силуэта она не сравнима. На теле MakeHuman формула даёт талию на 2–2,5 см больше
  ленты, бёдра — на 5–6 см: сечение бёдер MakeHuman «площе», чем у людей. Насколько формула точна на живых
  снимках, покажет сверка с лентой на реальных фото.
- **Подгонка модели** (`PhotoFitter.cs`, кнопка «Подогнать модель по фото»). Подбирает наклон таза, прогиб,
  сутулость, живот, ягодицы, глубину корпуса и V-силуэт так, чтобы силуэт модели совпал со снимками;
  обхваты остаются замерами. Спереди сравнивается ширина от ягодиц до подмышек (выше в силуэт входят руки),
  сбоку — перед и спина от ягодиц до основания шеи. Метод Левенберга — Марквардта с численными производными;
  масштаб и сдвиг снимка находятся точно, сдвиг уровней по высоте (волосы, перспектива) — тоже параметр.
  Расхождения больше 1 см весят меньше (функция Хьюбера), слабая тяга к нейтральным значениям не даёт
  параметрам блуждать. Итог сразу применяется к «Осанке и форме», края модели рисуются поверх снимков
  оранжевым пунктиром, «Вернуть как было» — откат. В браузере — 6–10 с.

**Проверка «туда и обратно»** (`PhotoFitTests.cs`): тело с известными осанкой и формой → синтетические
снимки (перспективная камера, маска как у MediaPipe) → разбор → подгонка с нейтральных значений.

| Камера | Расхождение силуэтов | Углы | Форма |
|---|---|---|---|
| 50 м, почти без перспективы | 0,9 → 0,06 см | до 2,1° | до 0,03 |
| 3 м, как телефон, ноги вместе | 1,7 → 0,13 см | до 1,3° | живот 0,01, остальное до 0,2 |
| 3 м, ступни разведены на 40 см | 1,3 → 0,3 см | сутулость верно, наклон таза и прогиб путаются | живот путается |

Отсюда просьба снимать сбоку с ногами вместе: ближняя стопа на 20 см ближе к камере опускает низ фигуры
на кадре и сбивает масштаб по росту на 4–5 %. Синтетика — это сама модель MakeHuman, поэтому тест проверяет
подгонку, а не то, насколько MakeHuman похож на конкретного человека. Это покажут реальные снимки.

### Прогресс по фото и факт против прогноза

- **Сравнение сессий** (`PhotoComparer.cs`). В разборе сессии — «Сравнить с:» и любая другая разобранная
  сессия. Снимки совмещаются по макушке и масштабу роста, сбоку — ещё и по лопаткам (66–80 % роста): там
  спина меняется меньше всего, а поясница и живот — сильнее всего. Прежний контур рисуется белым пунктиром
  на открытых снимках. Карта изменений — два графика с общей шкалой: ширина спереди и глубина сбоку по
  полосам в 2 % роста от шеи до бёдер; синим влево — ушло, красным вправо — прибавилось; подсказка при
  наведении делит глубину на перед и спину. Рядом таблица «было → стало»: вес и обхваты талии и бёдер по фото.
  Ошибка обхватов по фото (±1,5–1,8 см) у одного человека почти постоянна, поэтому разница между сессиями
  точнее самих обхватов; разница в полсантиметра и меньше — шум (поза, дыхание, свет).
- **Факт против прогноза** (`ForecastTracking.cs`). «Начать план сегодня» фиксирует дату начала и замеры
  на этот день — прогноз дальше считается от них, а не уезжает вслед за текущим весом. Факты — записи
  веса («Вес сегодня», по одной на день) и фотосессии (вес на момент съёмки, а у разобранных — ещё талия
  и бёдра по фото). Прогноз на дату факта — по дробной неделе, между неделями линейно; обхваты — через
  изменение жира и безжировой массы на эту дату, как у итога прогноза. Факты — кружки на графике веса
  выбранной гипотезы; таблица «Дата / Неделя / Прогноз / Факт / Разница» и итог по последнему факту:
  впереди или позади прогноза. Вода и гликоген есть на весах, но не на обхватах, поэтому в первые недели
  вес расходится с прогнозом сильнее обхватов.
- **Прогноз на фото** (`PhotoWarp.cs`, `warp.js`). Чип «Прогноз: …» над снимками разбора. Обе модели
  MakeHuman — «сейчас» и итог выбранной гипотезы — режутся на тех же уровнях, что и снимок, и разница
  в сантиметрах переносится на края силуэта: спереди каждый край сдвигается на половину изменения ширины,
  сбоку перед и спина — на свои изменения. Строки снимка растягиваются кусочно-линейно, фон рядом с телом
  тянется вместе с краем, дальше снимок не меняется. По высоте изменения сглажены и к краям туловища
  (бёдра, основание шеи) сходят на нет — без ступенек. Лицо, руки и ноги не меняются: это иллюстрация
  прогноза, а не обещание. В браузере — меньше секунды.
- **Защита фото.** Карточка «Защита» на вкладке «Фото»:
  - **PIN-код** (4–8 цифр) шифрует снимки и превью в IndexedDB: AES-GCM 256, ключ из PIN-кода через
    PBKDF2-SHA256 (600 000 итераций, случайная соль устройства). Ключ неизвлекаемый и живёт только в памяти
    вкладки: снимки закрываются после перезагрузки, кнопкой «Закрыть снимки» и через 2 минуты в фоне —
    расшифрованные копии при этом освобождаются. Неверный PIN-код отличает зашифрованная проверочная
    запись. Включение и снятие защиты перешифровывают все снимки одной транзакцией вместе с записью PIN-кода.
    Даты, вес и итоги разбора не шифруются: по ним строятся графики без PIN-кода. Забытый PIN-код не
    восстановить — «Удалить все фото» удаляет и его, после чего можно загрузить архив. Архив zip — обычные
    JPEG без шифрования, интерфейс об этом предупреждает.
  - **Размытие** — снимки размыты, пока на них не нажмёшь (контуры разбора видны и так), превью — всегда.
  - **Водяной знак** «личное фото · не пересылать» поверх снимков. Запретить снимок экрана веб-страница не
    может; знак останется на нём.
  - Пока вкладка в фоне, снимки размыты — в переключателе приложений их не видно.

  PIN-код защищает от случайного взгляда и чужих рук, а не от взлома устройства: тот, кто может
  выполнить код на странице во время работы с открытыми снимками, увидит и их. Поэтому лучше включить ещё
  и блокировку самого телефона.

### Как устроен манекен

Запасной вариант (переключатель «Манекен»): не анатомия, а гладкий манекен, у которого обхваты на модели
совпадают с введёнными (тест: ≤ 1 %). Строится за 10–20 мс и служит эталоном для проверки замеров.

- **Высоты и длины** — доли роста по Drillis & Contini (в изложении Winter, «Biomechanics and Motor
  Control of Human Movement»): плечи 0,818·H, тазобедренный сустав 0,530·H, колено 0,285·H, плечо 0,186·H,
  предплечье 0,146·H, бедро 0,245·H, голень 0,246·H. Ширины плеч (0,259·H) и таза (0,191·H) задают
  положение суставов. Уровни груди, пупка, ягодиц, промежности и подмышек — средние ANSUR II (ниже);
  остальных уровней нет и там, их доли оценены и помечены в `Proportions.cs`.
- **Туловище** — эллиптические сечения на уровнях пах, ягодицы, талия, низ груди, грудь, подмышки, плечи,
  основание шеи. Для каждого уровня задано соотношение глубина/ширина. Оно зависит от пола, а у груди,
  низа груди, талии и бёдер ещё и от ИМТ: у полных сечения круглее, с тем же наклоном, что у отношения
  глубины к ширине у людей ANSUR II (+0,9…1,3 % на единицу ИМТ). Полуоси подбираются так, чтобы периметр
  по Рамануджану равнялся обхвату. Между уровнями — монотонная кубическая интерполяция (аналог Catmull-Rom
  без «перелётов»), 48 точек по окружности.
- **Руки, ноги, шея** — трубки с круглыми сечениями. Плечо и бедро — из ввода, голень и запястье — из ввода,
  если указаны. Предплечье, низ бедра, щиколотка и неуказанные голень, запястье и шея — по ANSUR II
  (`AnsurGirths.cs`); дельта, локоть, середина бедра — оценки (`SectionShapes.cs`).
  Голова, кисти и стопы — суперэллипсоиды. Поза — A-поза, руки под 35° к вертикали.
- **Сетка** строится в C# (~19,6 тыс. вершин) и уходит в JS бинарно (`[JSImport]` + MemoryView).
  JS только рисует: three.js 0.186.1 лежит в `wwwroot/lib/three` и подключён через import map.
- **Объём** — сумма замкнутых частей по теореме о дивергенции минус их перекрытия (корни рук и ног внутри
  туловища и т. п.; перекрытия считаются сеткой точек). Пересечение бёдер между собой не вычитается:
  у полных бёдра сплющиваются друг о друга, но ткань никуда не девается.

### Пропорции по данным ANSUR II

ANSUR II — антропометрическое обследование армии США 2010–2012 гг., открытые данные: 4082 мужчины
и 1986 женщин, 93 замера. Выборка военная — моложе и спортивнее населения в среднем, но вес от 36 до 144 кг.

- **Обхваты, которых нет в замерах** (`AnsurGirths.cs`) — линейные регрессии по росту и весу, для голени
  и низа бедра — ещё по обхвату бедра. Против прежних оценок:

  | Обхват | Было: сдвиг / ошибка | Стало: ошибка |
  |---|---|---|
  | Голень, женщины | +2,4 / 3,1 см | 1,7 см |
  | Голень, мужчины | +1,7 / 2,5 см | 1,6 см |
  | Щиколотка | −1,2…−1,4 / 1,7–1,8 см | 1,0–1,2 см |
  | Запястье, шея, низ бедра | ошибка 0,7–2,0 см | на 10–25 % точнее |

- **Уровни** груди, пупка, ягодиц, промежности и подмышек — средние ANSUR II. Сильнее всего поправился
  уровень груди у мужчин: 0,735 роста вместо 0,720 (на 2,7 см выше).
- **Пересчёт.** Сами данные в репозиторий не входят. Скачайте `ANSUR II MALE Public.csv` и
  `ANSUR II FEMALE Public.csv` (например, с [официальной страницы](https://ph.health.mil/topics/workplacehealth/ergo/Pages/Anthropometric-Database.aspx))
  и запустите:

  ```bash
  dotnet run --project tools/WorkoutCalculator.AnsurFit -- "ANSUR II MALE Public.csv" "ANSUR II FEMALE Public.csv"
  ```

  Утилита печатает коэффициенты и уровни и завершается с ошибкой, если таблица в коде с ними не совпадает.
- **Проверка моделей на людях.** С флагом `--validate` (в конце команды выше) утилита строит тело каждого
  человека по его росту, весу и обхватам: % жира — по формуле ВМС США, бицепс в ANSUR меряют напряжённым,
  расслабленный считается на 1,5 см меньше. Манекен проверяется на всех (6059 человек), MakeHuman — на
  выборке по 300 человек каждого пола. Печатается отклонение объёма от объёма по весу по группам ИМТ, толщина
  слоя MakeHuman и какие обхваты не подогнались. Поправка объёма манекена по ИМТ (ниже) подбирается заново
  и сверяется с кодом: при расхождении утилита завершается с ошибкой. Без данных MakeHuman проверяется
  только манекен.

### Проверка замеров

- Объём манекена сравнивается с объёмом из веса: плотность по Сири D = 495 / (%жира + 450) г/см³,
  объём = вес / D **плюс воздух в лёгких** (3,0 л у мужчин, 2,4 л у женщин). Сетка — внешний объём тела,
  а плотность по Сири считается без воздуха; без этой поправки любой манекен был бы на 3–5 % «толще» веса.
- Объём для проверки всегда берётся у манекена, в том числе когда на экране MakeHuman: у MakeHuman объём
  подгоняется под вес слоем мягких тканей, поэтому сравнивать его с весом бессмысленно.
- **Поправка по ИМТ.** Даже у реальных людей манекен по их обхватам выходит то объёмнее, то меньше тела:
  у худых мужчин на ~5 % больше объёма по весу, у полных женщин на ~4 % меньше. Вероятные причины — живот
  между уровнями замеров и эллипс вместо настоящего сечения. Поэтому объём манекена делится на
  1 + a + b·(ИМТ − 25); a и b подобраны на людях ANSUR II (`ConsistencyChecker.MannequinBias`). С поправкой
  среднее отклонение в каждой группе ИМТ — от −0,2 до +0,6 %, разброс — 2,2 % у мужчин и 2,5 % у женщин.
- При расхождении больше 8 % (около трёх стандартных отклонений) — мягкая подсказка «замеры и вес плохо
  согласуются», не ошибка. У людей ANSUR II она срабатывает у 0–0,1 %, так что почти всегда это ошибка
  ввода, а не особенность фигуры. Свой % жира с весов или калипера тоже ошибается на несколько процентов.
- **% жира по обхватам** — формула ВМС США (Hodgdon & Beckett, 1984): у мужчин по шее и талии на уровне
  пупка, у женщин ещё по бёдрам, талия — в самом узком месте. Её ошибка — 3–4 % жира; если введённый
  % отличается от оценки больше чем на 7 %, появляется подсказка перепроверить. Без шеи формула не считается.
- Подсказки о неправдоподобных сочетаниях: талия больше груди при низком % жира, талия/рост против
  % жира, ИМТ против % жира, % жира ниже незаменимого, места замера бедра и плеча.

### Прогноз: модель и допущения

Расчёт по неделям, все константы с источниками — в `ForecastConstants.cs`.

- **Расход** = БМР по Миффлину — Сан Жеору (пересчитывается от текущего веса каждую неделю) × коэффициент
  бытовой активности + активные ккал тренировок. Кардио считает калькулятор (`EnergyCalculator`) тоже
  от текущего веса; силовая — 3,5 MET × 1 ч (Compendium of Physical Activities, 2011). Берутся только
  активные ккал: БМР за время тренировки уже входит в «БМР × коэффициент».
- **Адаптация обмена** (Hall et al., Lancet, 2011): если питание отличается от поддержания в начале плана,
  расход сразу меняется на 10 % от разницы (термический эффект пищи) и ещё на 14 % — постепенно,
  с постоянной времени 14 дней (адаптивный термогенез). Разница считается по всему дефициту или профициту
  плана, даже если его даёт кардио (у Холла — только питание; так проще и осторожнее). При −500 ккал
  в день вес за 12 недель уходит примерно на 20 % медленнее, чем без адаптации.
- **Энергия тканей** (Hall et al., Lancet, 2011): жир 9400 ккал/кг, безжировая масса 1800 ккал/кг.
- **Дефицит:** доля безжировой массы в потере — по правилу Форбса (Forbes, 2000; Hall, Br J Nutr, 2007):
  10,4 / (10,4 + жировая масса, кг), пересчёт каждую неделю. У полного человека почти всё уходит из жира,
  у худощавого — всё больше из мышц. Силовые тренировки уменьшают эту долю вчетверо (×0,25): что упражнения
  сильно сберегают мышцы при дефиците, показывают обзоры (например, Weinheimer et al., Nutr Rev, 2010),
  а сам коэффициент — оценка прототипа. Жир не опускается ниже незаменимого (3 % / 12 %).
- **Вода и гликоген:** запас ≈ 1,5 % безжировой массы (гликоген хранится с водой примерно 1 : 3).
  При дефиците он уходит за 1–2 недели (60 % оставшейся разницы в неделю), при профиците пополняется
  наполовину; полностью — при балансе от 1000 ккал/день, при меньшем пропорционально. Килограмм запаса
  даёт ~1000 ккал и покрывает часть дефицита. Поэтому в первые недели вес на весах падает быстрее, чем уходит
  жир. Вода и гликоген входят в вес, но не в обхваты; в результатах они показаны отдельной строкой.
- **Профицит:** мышцы растут только с силовыми и не быстрее потолка по стажу — нижняя граница диапазонов
  Алана Арагона: новичок 1 %, средний 0,5 %, опытный 0,25 % веса в месяц, у женщин вдвое меньше.
  (Его диапазоны — темпы общего набора веса, а не чистых мышц, поэтому взята нижняя граница.) Остаток — жир.
- **Обхваты:** изменение жира и мышц раскладывается по регионам (живот, грудь, ягодицы, ноги, руки, шея)
  по долям, зависящим от пола, и переводится в обхват через цилиндр V = C²·L/(4π) с неизменной длиной L.
  L берётся из раскладки манекена, поэтому объём модели-прогноза сходится с прогнозным весом.
  Доли одни и те же при наборе и потере — **локального жиросжигания нет**, «убрать только живот» нельзя.
  Указанная голень меняется пропорционально бедру, запястье (кости и сухожилия) не меняется.
- **Предупреждения:** темп похудения больше 1 % веса в неделю, калории ниже БМР, цель недостижима
  за срок, профицит без силовых, жир к концу срока ниже ~8 % (мужчины) / ~15 % (женщины).

Что модель **не** учитывает: что обмен у разных людей подстраивается по-разному (в модели — средние
коэффициенты Холла), колебания воды (соль, цикл, стресс), возраст в скорости набора мышц, гормоны
и реальное соблюдение плана. Поэтому в интерфейсе — подпись «грубая оценка, а не обещание».

### Публикация, офлайн и приватность

- **GitHub Pages.** `.github/workflows/pages.yml` при пуше в main прогоняет тесты, публикует веб-приложение
  (`dotnet publish -c Release`) и выкладывает на GitHub Pages. Один раз нужно включить в настройках
  репозитория: Settings → Pages → Build and deployment → Source: **GitHub Actions**. Адрес в `index.html`
  относительный (`<base href="./">`), поэтому одна и та же сборка работает и в корне сайта, и в подпапке
  `/trening/`.
- **Офлайн и установка (PWA).** `manifest.webmanifest` и иконки делают сайт устанавливаемым приложением.
  Service worker опубликованной версии (`service-worker.published.js`) при первом заходе кладёт в кэш все
  файлы приложения вместе с данными MakeHuman (~14 МБ) — дальше всё работает без сети. Когда выходит новая
  версия, она скачивается в фоне, и внизу появляется плашка «Вышла новая версия · Обновить». При
  `dotnet run` офлайн-кэш выключен, чтобы правки было видно сразу.
- **Данные не покидают устройство.** Сервера у приложения нет: сайт — только статические файлы, всё
  считается в браузере, профиль, гипотезы, вес и журнал тренировок хранятся в localStorage, фото — в IndexedDB этого браузера
  (с PIN-кодом — зашифрованными, см. «Защита фото»).
  Распознавание позы и разбор снимков тоже идут на устройстве: модель MediaPipe лежит в самом приложении. Политика безопасности (Content Security
  Policy в `index.html`) разрешает странице загружать только свои файлы и соединяться только со своим
  сервером — отправить данные на чужой сервер браузер не даст даже при ошибке в коде. Это не теория:
  MediaPipe после разбора снимков пытается отправить свою телеметрию на `odml.pa.googleapis.com` —
  браузер блокирует запрос (в консоли — ошибка политики безопасности), ничего не уходит. Это можно проверить:
  в инструментах разработчика браузера, вкладка «Сеть», нет ни одного прошедшего запроса к другим адресам.
- **Файлы среды .NET без хеша в имени** (`WasmFingerprintAssets=false`): иначе .NET ищет их через свою
  import map, а в документе может быть только одна — наша, для three.js. Версии файлов различает service
  worker: у каждой сборки свой кэш.
