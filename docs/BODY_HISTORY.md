# История тела

Вкладка/режим «История» хранит состояния тела отдельно от текущего профиля и прогноза. Стек: поверх #13 (`49d988fd65c14cd26712946b286a700a5e20a25e`), PR base `codex/strength-journal`. Персонализация прогноза и причинные выводы не добавлены.

## Факты и представления

`BodyModel/History/BodySnapshot` — immutable record с UUID, локальной `DateOnly`, источником `Manual / Photo / Imported`, `SnapshotQuality`, nullable весом, жиром, ростом, возрастом, полом, осанкой и формой. Обхваты — `ImmutableDictionary<Girth, GirthObservation>`; отсутствующий ключ означает отсутствие наблюдения. Нулевые значения не заменяют пропуски. Запись должна содержать хотя бы одно наблюдение, а не только демографические параметры. Все числовые значения конечны и проходят диапазонную валидацию.

`GirthObservation` хранит сантиметры, метод `Manual / PhotoDerived` и необязательный RMSE модели. Фотооценка явно отличается от измерения лентой. RMSE из существующей `PhotoGirths` — характеристика регрессии на ANSUR, не достоверность конкретной фотографии. Предупреждения разбора сохраняются в quality metadata. Числовой Confidence необязателен: приложение его не выдумывает.

`SnapshotVisuals.Build` создаёт новый `BodyProfile`. Известные поля копируются точно. Остальное заполняется отдельным детерминированным шаблоном/оценками ANSUR только для 3D, с перечнем заполненных полей. Текущий редактируемый профиль не участвует: старое тело не меняется при изменении сегодняшних настроек. Без пола используется явно обозначенный условный мужской шаблон. Частичная точка не позволяет восстановить точную внешность. Факты не изменяются, представление не записывается в storage.

## Ввод и импорт

- Новая ручная запись начинается с пустых значений. Кнопка заполнения текущим профилем создаёт проверяемый черновик; пользователь очищает неподтверждённые поля перед сохранением. Неуказанные шея/голень/запястье не подставляются из effective getters. Осанка и форма включаются отдельным явным подтверждением.
- Ручные сохранённые точки редактируются только через отдельный черновик и сохранение с прежним ID. Импортированные точки не редактируются автоматически. Удаление подтверждается в интерфейсе.
- «Импортировать вес и фото» читает старый `workoutcalc.weights.v1` строго и получает `PhotoStore.ListMeta()` из IndexedDB. Открытие приложения ничего не записывает. Невалидный источник отменяет весь импорт, старые данные сохраняются.
- Weight-only факт содержит только дату/вес. Уникальная ссылка — `weight:yyyy-MM-dd`.
- Фото импортируется только при наличии двух обработанных проекций, масштаба и доступных талии/бёдер. Сохраняются только эти derived values, параметры масштаба, качество, `PhotoSessionId`, ссылка `photo:<id>`. Старые weight/body-fat в PhotoMeta были копией текущего профиля: они **не импортируются как новые измерения**. UTC-время фотосессии преобразуется в календарную дату браузера один раз при импорте. Фото/превью не читаются и не копируются.
- Повторный импорт пропускает уже признанные ссылки. Изменение/удаление исходного веса или фото не переписывает сохранённую историю. Удалённая историческая точка не воскресает при повторном импорте. Для исправления импортированного факта можно удалить точку и создать ручную запись; синхронизация ревизий источника пока не реализована.

## Хранилище и восстановление

Отдельный ключ `workoutcalc.bodySnapshots.v1`:

```json
{ "schemaVersion": 1, "snapshots": [], "importedReferences": [] }
```

`ImportedReferences` — журнал импортов, включая удалённые точки. Обязательные поля envelope проверяются при чтении, дубликаты ID/ссылок и неизвестные версии блокируют запись. Ошибка чтения отличается от пустого хранилища; повреждённое содержимое никогда не заменяется дефолтом. Ошибка квоты оставляет черновик на экране.

Перед первым импортом `workoutcalc.bodySnapshots.v1.backup.before-import` получает точную исходную строку истории (либо пустой v1 envelope, если ключ отсутствовал). Существующая копия не перезаписывается. Ошибка создания копии отменяет импорт. Старый weight key и IndexedDB sessions/images вообще не изменяются.

Для ручного отката сначала экспортировать обе строки из инструментов браузера, затем восстановить основной ключ из `.backup.before-import` и перезагрузить страницу. Это возвращает историю до первого импорта; последующие записи истории будут отсутствовать в восстановленном представлении, поэтому сначала нужна копия текущего ключа. Исходные веса/фото сохраняются независимо. Для повреждённого payload сначала сохранить исходную строку; автоматического сброса/ремонта нет.

Используется тот же `IJournalStorage` / `BrowserJournalStorage`, что в strength journal: strict read и optimistic compare-exchange исходной строки. Известное изменение в другой вкладке отклоняет запись, черновик сохраняется. Это унаследованная синхронная защита localStorage, не межпроцессная транзакция/Web Locks; одновременно исполняющиеся проверки в разных вкладках теоретически могут соревноваться.

## Timeline, сравнение, тренировки

`BodyTimeline` сортирует по дате и ID, сохраняет выбор при обновлении, ограничивает навигацию концами списка. Маркеры и ползунок выбирают только сохранённые точки. `SnapshotComparison` вычисляет дельту только при наличии обоих значений. «Нет пары» не заменяется нулём; фотооценки помечаются.

`Home.History.cs` подключает существующий viewer и его два renderer slots/ghost. Режимы `history / historyCompare` отделены от `current / forecast / compare`; history никогда не меняет `_profile`, forecast DTO или forecast cache. Отложенные сборки текущего/прогнозного тела не отправляются поверх истории. При возврате восстанавливаются текущая/прогнозная геометрия и heatmap. Exercise animation при входе останавливается и не возобновляется автоматически. Доступны MakeHuman и манекен.

`WorkoutPeriodSummary` использует календарный интервал **[от, до] включительно**. Силовые сессии считаются, если содержат хотя бы один completed set; подходы, reps, внешний тоннаж и top groups получены через `StrengthAggregation` и агрегацию raw до нормализации. Собственный вес в тоннаж не выдумывается. Кардио: число записей, минуты и сохранённая оценка **active kcal**, не общий расход и не данные часов. Это сводка журнала за период, а не объяснение изменений тела. При ошибке strength storage UI показывает недоступность силовой сводки.

Автоматический playback отложен: есть точечный scrub и API `SnapshotVisuals.Interpolate(a,b,t)`, возвращающий только визуальный `BodyProfile`. Он не создаёт промежуточные «измеренные» точки и не используется для вычисления дельт.

## Проверки

```sh
dotnet build WorkoutCalculator.sln -c Release
dotnet test WorkoutCalculator.sln -c Release --no-build
node --test tests/js/*.test.mjs
node tests/browser/skeletal-smoke.cjs
node tests/browser/strength-smoke.cjs
node tests/browser/history-smoke.cjs
```

Для browser smoke приложение должно работать на `APP_URL` (по умолчанию `http://127.0.0.1:5256`), нужен Playwright/Chromium. `BROWSER_CHANNEL`/`BROWSER_PATH` выбирают установленный браузер; `HISTORY_SCREENSHOT_PREFIX` сохраняет виды 320/390/1400 px. Все три smoke включены в CI. Новый smoke проверяет реальные Blazor/WASM, две созданные точки, distinct 3D, overlay/side-by-side, смену модели, частичный импорт, локальную дату фото, неизменность старых keys и количества фото, reload, stale-tab, corruption и возврат в старые режимы. Unit-тесты проверяют модель, диапазоны, отсутствие мутаций, сравнение, timeline, сводку периода, backup/rollback/idempotency и отказы storage.
