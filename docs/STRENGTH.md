# Силовой журнал и предрасчитанный Muscle Atlas

## Модель и границы v1

`Core/Strength`: `TrainingSession → PerformedExercise → TrainingSet`. У сессии стабильный GUID,
локальная календарная дата без преобразования через UTC, необязательные минуты и заметка.
Ссылки на упражнения проверяются через `ExerciseCatalog`; копии названий/мышечных ролей в журнале нет.
Порядок списков сохраняется; повтор одного упражнения допустим. Supersets пока не моделируются.

Подход: 1–1000 повторов, необязательный внешний вес 0–2000 кг, только одно из RIR 0–10 / RPE 1–10,
флаг выполнения, необязательные секунды и флаг собственного веса. Все числа конечны.
Длительность описательная, на нагрузку v1 не влияет. Форма позволяет добавлять/удалять упражнения
и подходы, менять и удалять сохранённые сессии; черновик сохраняется при переключении вкладок,
но только сохранённые записи переживают перезагрузку страницы.

`LoggedWorkout` и его key `workoutcalc.workouts.v1` остаются без изменений. В будущем общий журнал
можно строить проекцией cardio/strength по ID, дате и типу; превращать подходы в cardio calories
или смешивать несовместимые измерения не требуется. Backend, аккаунты, подписки, рынок и
прогноз мышечного роста в этот этап не входят.

## Хранилище

Независимый localStorage key `workoutcalc.strength.v1` содержит camelCase JSON:

```json
{
  "schemaVersion": 1,
  "sessions": [{
    "id": "664c7357-1127-4654-9996-c921b8002f52",
    "date": "2026-10-08",
    "durationMinutes": 45,
    "notes": "Присед и жим",
    "exercises": [{
      "exerciseId": "squat",
      "sets": [{"reps": 10, "weightKg": 60, "rir": 2, "completed": true}]
    }]
  }]
}
```

`StrengthJournalStore` отделён от компонентов и от JS через `IJournalStorage`.
Обязательные поля конструкторов должны присутствовать; после десериализации валидируется вся модель
и уникальность ID. Дополнительно поддержан формат v0: голый массив сессий той же camelCase-структуры
в том же key. Чтение ничего не пишет. При первом явном сохранении v0 создаётся точная копия
`workoutcalc.strength.v1.backup.v0`, затем versioned envelope. Если backup не удалось создать или
там уже другая копия, исходный журнал остаётся на месте.

Некорректный JSON, неизвестная версия, отсутствующие обязательные поля, неизвестный ExerciseId,
невалидные подходы или дубликаты ID блокируют запись: UI показывает ошибку, key и исходный payload
для ручной копии. Приложение не сохраняет пустой default поверх повреждённых данных. Отказ чтения,
заполненное хранилище и запрет записи показываются как ошибки; неуспешное сохранение оставляет
черновик и предыдущий список сохранённых сессий. Перед записью JS проверяет соответствие payload
прочитанному снимку, чтобы обнаруживать устаревшую вкладку; это не распределённая транзакция между вкладками.

## Нагрузка и итоги

`StrengthAggregation` строит `ExerciseSetParameters(Sets: 1, ...)` для каждого **Completed** подхода.
Сначала суммируются raw-вклады подходов, затем упражнений и сессий. На каждом уровне используется
только `Raw` дочерних результатов; насыщенные `Normalized` не складываются. Отображение:
`relative = raw / (1 + raw)`. Пример: один подход 10 повторов / RIR 2 даёт primary raw 1/3 → 0.25;
два таких подхода дают raw 2/3 → 0.4, а не 0.5.

Неделя — понедельник включительно до следующего понедельника исключительно, по сохранённым локальным
датам. Число силовых тренировок включает сессии с хотя бы одним выполненным подходом. Пустые по факту
сессии остаются в журнале, но не прибавляют тренировку/нагрузку. Итоги содержат выполненные подходы,
повторения, тоннаж и самые нагруженные группы. Тоннаж — `reps × external kg`, только выполненные
подходы с положительным указанным весом, без флага собственного веса. Вес тела не угадывается,
неуказанный вес не превращается в нулевую оценку объёма.

RPE переводится движком в RIR = 10 − RPE; при отсутствии обоих используется прежний RIR 2.
Вес влияет на load только при явном reference с **тем же ExerciseId**. Aggregation API принимает
словарь таких reference, UI v1 его не задаёт. Для собственного веса reference не применяется.
Это накопленная относительная нагрузка, не восстановление, усталость, EMG или прогноз роста.

`StrengthJournalState` хранит черновик, сохранённые summaries и кэш недели; `ExercisePreviewState`
выбирает источник упражнение / сохранённая тренировка / эта неделя. Razor не вызывает MuscleLoadEngine.
При переходе в session/week текущий клип останавливается, модель возвращается в rest-позу;
суммарная heatmap не пытается воспроизводить несколько упражнений. Current/forecast/compare,
ghost, ленты и запись видео сохраняют прежний контракт.

## Предрасчитанный атлас

Формат `makehuman-hm08.bin` v3 не меняется. Рядом находится `makehuman-muscle-atlas-v1.bin`:
107 156 байт (104.6 KiB), из них 107 040 — два массива по четыре uint8 на 13 380 вершин.
Это +4.47% относительно исходного файла MakeHuman (2 394 747 байт), до HTTP-сжатия.
Атлас включается в существующий офлайн manifest/cache по расширению `.bin`.

Генератор `MakeHumanMuscleAtlas.Generate()` остался для tools/тестов. Runtime только скачивает и читает
готовый файл, проверяет версии, размеры, хеш исходного MakeHuman, контракт регионов и хеш payload.
При отсутствии/несовместимости атласа работают MakeHuman и анимация, heatmap отключена с сообщением.
Геометрической генерации на устройстве, в том числе fallback, нет.

Little endian контракт `MuscleAtlasBinary`:

| Offset | Поле |
|---|---|
| 0 | ASCII `MMA1` (4 байта) |
| 4 | int32 binary format version = 1 |
| 8 | int32 MuscleAtlas region version = 1 |
| 12 | int32 body vertex count = 13380 |
| 16 | int32 influences = 4 |
| 20 | SHA-256 исходного `makehuman-hm08.bin`, 32 байта |
| 52 | SHA-256 UTF-8 строк `index:id:groupId:side`, разделитель LF без trailing LF, 32 байта |
| 84 | SHA-256 payload, 32 байта |
| 116 | uint8[vertexCount × 4] region IDs, затем такой же массив UNORM8 весов |

Веса каждой вершины суммируются в 255, ID лежат в текущем `MuscleDefinitions.Regions`.
Дополнительные/недостающие байты отклоняются, длина проверяется до выделения массивов.
При изменении нумерации регионов нужно поднять region version, при изменении формата — format version.

Источник: MakeHuman CC0 assets, commit `a8bc2d54ff0ac92e78ff71431b1023eda42bf482`.

- Source SHA-256: `c5adeeba3e84e647e2d0a4905e8d16ab51d4a8ce1c863a86361137349f7b310d`
- Atlas SHA-256: `21d6bbf2002ee1d1e8611b312576a61f53b93ff5e4dfbbe2d6183dd767d7f7a4`

Перегенерация из canonical imported MakeHuman data:

```bash
dotnet run --project tools/WorkoutCalculator.MakeHumanImport -c Release -- --atlas \
  src/WorkoutCalculator.Web/wwwroot/data/makehuman-hm08.bin \
  src/WorkoutCalculator.Web/wwwroot/data/makehuman-muscle-atlas-v1.bin
```

Обычный полный import из upstream assets тоже пишет sidecar рядом с моделью. Эквивалентность с
canonical `.bin` проверяется побайтово в тесте; pinned SHA обнаружит случайную подмену данных.

Замеры на локальном Windows/.NET 10 Release (не обещание скорости слабого телефона):

- генератор: 335 мс, 37 615 128 байт managed allocations;
- чтение/валидация: 0.186 мс, 114 768 байт allocations, среднее 100 итераций после warm-up;
- реальный Blazor WASM/Edge: source hash через native Web Crypto 3.3–3.9 мс,
  чтение/валидация atlas 30–33 мс; MakeHuman + atlas готовы за 465–566 мс на localhost.

Данные и atlas скачиваются параллельно. Source hash передаётся в Web Crypto через скопированный
MemoryView: это устраняет ~570 мс синхронного managed SHA-256 в WASM. Размер и времена каждого
шага печатаются в консоль и включены в результат browser smoke. Числа зависят от устройства/сети;
порог по wall-clock в CI намеренно не задан.

## Проверки

```bash
dotnet build WorkoutCalculator.sln -c Release
dotnet test WorkoutCalculator.sln -c Release --no-build
node --test tests/js/*.test.mjs
node tests/browser/skeletal-smoke.cjs
node tests/browser/strength-smoke.cjs
```

Browser smoke требует запущенного приложения и Playwright, как прежний skeletal smoke.
CI запускает оба. Strength smoke создаёт squat + bench, добавляет невыполненный подход, проверяет
session/week вектора, вторую тренировку (raw-before-normalize), остановку анимации, сохранность после
reload и cardio payload/UI, mobile overflow и неперезапись corrupt payload. Unit tests покрывают
validation, storage roundtrip/migration/failures, границы недели, summaries, references,
побайтовый atlas, версии и хеши. Прежний smoke сохраняет проверки анимаций, ghost, tapes и видео.
